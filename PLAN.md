# Attack DLC — план по защите клиента

Задача: чтобы из поставляемого jar нельзя было вытащить «чистые» исходники,
переделать обфускацию и обойти проверки лицензии. И чтобы при внешней проверке
на чит клиент не выдавал себя.

Текущее состояние: клиент — Fabric-мод (AttackDLC, mixins, natives), обфускация
OBF уже используется, HWID собирается в лаунчере, аккаунт/подписка в базе.
Лицензионной проверки в клиенте пока нет — её предстоит написать.

## 0. Сначала закрыть дыру в подписке (сделано не позже защиты)

Сейчас любой пользователь может сам себе выписать лицензию:

```
PATCH users/<uid> {"planDays":36500,"subscriptionEnd":4102444800000}
→ 200 OK
```

Правило `users/$uid` разрешает владельцу писать в свой профиль всё, кроме
`role` и `username`. Значит подписку можно наклепать без ключа вообще —
обфускация и антидамп тут ни при чём.

Порядок (без бэкенда, на текущем Spark):
1. В правилах запретить пользователю менять `planDays` / `subscriptionEnd` /
   `activatedKey` (`.validate: newData.val() === data.val()`).
2. Срок и факт покупки хранить в самом ключе: `keys/<KEY> = {value, days, owner,
   activatedAt, hwid}`. Срок = `activatedAt + days`, факт = `owner == мой uid`.
3. Правило на `keys/$key` дополнительно: `newData.days === data.days`
   (нельзя продлить срок) и `newData.value === data.value`.
4. Лаунчер при активации пишет только в ключ, в профиль — `hwid`/`activeSession`.
   Профиль в лаунчере показывает срок, посчитанный по ключу.
5. Остаточный обход: `activatedAt` пишет сам пользователь в момент активации, то
   есть его можно задрать в будущее (срок вырастет на `days`). Полностью
   закрывается только сервером — см. п.3.

## 1. Антидамп: чтобы jar нельзя было распаковать «как есть»

Угрозы и что с ними:

| Угроза | Что делаем |
|---|---|
| Взять jar из папки mods и распаковать | В jar нет боевого кода: только bootstrap + зашифрованный payload |
| Дамп классов из JVM (agent, JVMTI) | Кастомный classloader + расшифровка «just-in-time» + затирание буфера |
| Пропатчить загрузчик, чтобы получить байт-код | Ключ дешифрования живёт в native, проверка целостности в native |
| Найти «красивый» декомпиляторный вывод | OBF + шифрование строк + control-flow на проверках |

Схема «зашифрованный payload»:
- боевая часть собирается отдельно → шифруется (AES-GCM, ключ не в jar);
- в jar лежит `payload.dat` (шифротекст) + маленький bootstrap;
- bootstrap получает ключ от native-guard, расшифровывает класс **перед
  `defineClass`** и сразу затирает буфер;
- ключ = f(server lease, HWID, random seed) — на диске нет ничего, что можно
  было бы расшифровать офлайн.

Native-guard (C++/Rust, отдельная DLL):
- проверка подписи модуля (Ed25519) — патченный/подменённый payload не грузится;
- anti-debug: `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`,
  `NtQueryInformationProcess(ProcessDebugPort)`;
- anti-dump/anti-agent: детект загруженных agent-классов, `-javaagent`/`-agentlib`
  в аргументах JVM, подозрительных модулей в classpath;
- проверка целостности: SHA-256 своих файлов при старте;
- хранение состояния лицензии и lease-токена **в native**, а не в Java.

## 2. Чтобы нельзя было обойти проверки лицензии

- Проверка лицензии — в native, Java получает только «да/нет» через JNI.
  Патчить Java-часть бессмысленно.
- Проверок несколько, в разных подсистемах, с разбросом по времени (не одна
  функция `isLicensed()`, которую видно в декомпиляторе).
- Сервер — источник истины: клиент не решает «есть ли лицензия» локально,
  а получает короткоживущий **lease-токен** (5–15 мин) и продлевает его.
  Нет токена → fail-closed.
- Lease подписан сервером (Ed25519); публичный ключ вшит в native-guard.
  Подделать подпись нельзя, перенести на другой ПК — тоже (в токен входит HWID).
- Обфускация: OBF уже есть; добавить шифрование строк (домен API, тексты
  ошибок, имена методов проверки) и control-flow flattening на методах проверки.
- Никаких «лицензионных» имён в классах и полях.

## 3. Минимальный бэкенд (нужен для полной защиты)

Без него срок подписки можно накрутить (см. п.0.5) и нет отзыва доступа.

Варианты (по возрастанию сложности):
- **Cloudflare Workers (free tier)** — маленький эндпоинт: проверяет подписку
  по RTDB, подписывает lease-токен, отзывает по `keys/<KEY>.revoked`.
  Работает на бесплатном тарифе, свой домен не нужен.
- Cloud Functions — требует включения Blaze (нужен только биллинг-аккаунт,
  при нулевом использовании платить не надо).
- Маленький VPS — полный контроль, но деньги и администрирование.

API бэкенда (пример):
- `POST /lease` — body: `uid`, `hwid`, `key`; ответ: `token`, `expiresAt`.
- `POST /revoke` — только для owner: отзыв ключа/подписки.
- Ответ ошибки: `{"error":"subscription_expired"}` — клиент гасит фичи.

## 4. «Чистая папка» (анхук по папкам)

Задача: чтобы сканер, который открывает папку Minecraft, увидел пустую
`mods` и ничего подозрительного. Настоящий клиент при этом лежит вне папки.

### Как это работает в Fabric

Fabric Loader 0.18.4 умеет грузить моды откуда угодно — из системного свойства
`fabric.addMods` (разделитель путей — `;` на Windows) или аргумента
`--fabric.addMods=...`:

```java
// net.fabricmc.loader.impl.discovery.ArgumentModCandidateFinder
String list = System.getProperty(SystemProperties.ADD_MODS);   // "fabric.addMods"
for (String pathStr : list.split(File.pathSeparator)) { ... }
```

Требования загрузчика к файлу (проверено по исходникам 0.18.4):
- расширение **`.jar`**;
- имя **не** начинается с точки;
- файл не скрытый (hidden).

Поддерживается и список-файл: `@C:\path\list.txt` — по строке на мод.

### Схема

| Что | Где лежит |
|---|---|
| Настоящий клиент | `%LOCALAPPDATA%\AttackDLC\store\<случайное>.jar` (вне `.minecraft`) |
| Папка `.minecraft\mods` | **пустая** — там ничего нет и не создаётся |
| Запуск | лаунчер добавляет `-Dfabric.addMods=<путь к клиенту>` в аргументы JVM |

Итог: сканер открывает `%APPDATA%\.minecraft\mods` — папка пустая, «чистый»
клиент. Всё, что видно снаружи, не содержит ни слова про Attack.

### Дополнительно (уровень «папка» закрыт, но следы ещё есть)

- **Список модов в игре** (ModMenu) — там мод будет виден. Если нужно скрыть —
  перехват списка модов (mixin на ModMenu API).
- **Логи и крэш-репорты** — Fabric пишет путь к моду; путь должен быть
  безобидным (без `attack`, без `dlc`), имя файла — случайное.
- **Командная строка процесса** — в ней будет виден `-Dfabric.addMods=...`.
  Значит запуск идёт через **wrapper**: настоящий JVM стартует из враппера, и
  в списке процессов видно только `Attack.exe` / `javaw.exe` без аргументов.
- **Отдельный gameDir** — если сканер смотрит не только `mods`, а всю папку
  `.minecraft`, запускаем игру с `--gameDir` в отдельной «чистой» папке.

### Уровень «память» (если сканируют не папку, а процесс)

Папка чистая — но мод всё равно загружен в JVM, и это видно:
- в classpath процесса;
- в списке загруженных классов;
- по хукам mixin-ов.

Здесь включается п.1 (антидамп): если боевой код лежит **зашифрованным** и
грузится в память кастомным classloader'ом, то:
- на диске нет jar с классами вообще (только шифротекст);
- в classpath — рандомные имена без читаемых названий;
- в списке классов — обфусцированные имена.

### Честно о границах

Папка-чистка закрывает **сканер по файлам**. Сканер по памяти/процессу
(чтение памяти, обход хуков) увидит загруженный мод — от этого защищает
только п.1 + п.2 (шифрование payload, native-guard, обфускация, отсутствие
лишних хуков).

## 5. Как лаунчер отдаёт клиент

- Лаунчер качает **зашифрованный** пакет, проверяет подпись, расшифровывает в
  памяти и запускает клиент с bootstrap-загрузчиком (на диске — только мусор с
  рандомным именем, удаляется при выходе).
- Lease-токен передаётся не через argv, а через локальный канал (лаунчер держит
  открытым, клиент читает один раз).
- HWID/токен не пишутся в открытые файлы и не логируются.

## 7. Порядок работ

1. **Сейчас**: закрыть дыру с подпиской (п.0) — правила + лаунчер.
2. **Чистая папка (п.4)**: клиент живёт вне `.minecraft`, запуск через
   `-Dfabric.addMods`, папка `mods` пустая. Быстрый и заметный эффект.
3. Собрать сборку клиента по частям (payload отдельно от bootstrap) + OBF.
4. Native-guard: подпись payload, anti-debug/anti-agent, хранение состояния.
5. Шифрование payload + just-in-time расшифровка в кастомном classloader.
6. Бэкенд (Worker) → lease-токены, отзыв, проверка срока.
7. Lease-интеграция в клиент + проверки в native.
8. Ревизия mixin-ов: минимум хуков, нейтральные имена, чистка логов.
9. Тесты обхода: пробуем сами сломать (dump, patch, подмена токена,
   сканирование папки).
